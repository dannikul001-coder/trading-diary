# Второй Trading Diary — V3: прибыльные сигналы и точная хронология

Дата: 25.10.2026. Исходная сборка: `trading-diary-automated-design-v2-20261025.zip`.

## Назначение

По уточнению пользователя во втором дневнике **все завершённые сделки прибыльные**. Поэтому в Dashboard больше нет P&L, win rate, просадок и статистики проигрышей. Вместо этого показываются реальные доходы, ставки, общие возвраты, капитал, доступный баланс, резерв, бонусы, частота сигналов и детальная хронология.

При этом отрицательное движение денег (снятие или резервирование ставки) **не означает убыточную сделку**.

## Что фактически изменилось

- `js/automated-diary.js`: новая модель расчётов в **целых микроединицах (`BigInt`)**, учёт отдельного движения каждой ставки и полного возврата при закрытии; операции сортируются по UTC timestamp до секунды; операции с одним временем упорядочиваются однозначно; разграничиваются доступный баланс, резерв и общий капитал. Для графиков значения переводятся в Number лишь при отображении.
- Сделки: времена открытия и закрытия редактируются до **секунды**; индивидуальный ID в списке, индивидуальное закрытие по ID и проверка положительного дохода. Серверная функция однократно закрывает только открытую сделку.
- Финансы: фактические дата/время пополнения и снятия до секунды; на ленте каждый отдельный расход ставки и возврат, баланс **после каждого** события; возможность исправить время и сумму финансовой операции с серверной проверкой всей истории и журналом изменений; CSV с UTC-временем и остатком.
- Сигналы: календарь **одного выбранного дня**, кнопки предыдущего/следующего дня и «Сегодня», события сгруппированы по часам, показ времени до секунды. Поддерживаются более 8 событий в день.
- Dashboard: показатели **только по подтверждённым данным**; отдельные показатели по резерву, общему капиталу, заработанному доходу, количеству сделок, суммам ставок/возвратов и бонусам. Проблемные исторические данные выделяются для проверки, не переписываются.
- Адаптивный вид: таблица остаётся прокручиваемой внутри карточки и не растягивает страницу телефона.
- `sw.js`: новый PWA-cache key.
- `supabase/automated_diary_v2_timeline.sql`: отдельная **аддитивная** миграция, дополнительные поля `operated_at`, `operated_at_inferred`, `request_id`, отдельная история коррекций и серверные атомарные операции для сделок/финансов с проверкой хронологического остатка.

## Действия перед использованием финансовых операций

1. Сохранить **резервную копию Supabase** (как минимум второго дневника и метаданных).
2. Убедиться, что первоначальная миграция `supabase/automated_diary_v1.sql` уже выполнена.
3. На **тестовом экземпляре** Supabase открыть SQL Editor и **однократно** запустить `supabase/automated_diary_v2_timeline.sql`, затем проверить создание/закрытие сделки, пополнение, вывод и корректировку времени на тестовых данных.
4. После проверки и отдельно согласованной публикации применить миграцию к рабочему Supabase. Новая версия требует миграцию для записи сделок и финансовых операций — при отсутствии функций сообщает пользователю об этом и **не возвращается** к небезопасной старой записи.
5. Сверить фактические времена **старых** пополнений: исходная v1 не хранила время операции, только `created_at`. Миграция переносит старое `created_at` в `operated_at` с флагом `operated_at_inferred=true`. Это **не подтверждённое время реального пополнения**. Записи нужно проверить и при необходимости исправить через финансы; изменения заносятся в журнал.

Применять SQL повторно без необходимости не следует. **Никакая миграция реально не запускалась в этой сессии.**

## Бухгалтерские правила

- При открытии сделки доступный баланс уменьшается на **ставку** и увеличивается **резерв**.
- При закрытии уменьшается резерв, в доступный баланс приходит **полный возврат** (= ставка + прибыль), а доходом считается только разница.
- В момент пополнения/снятия доступный баланс меняется на сумму операции, независимо от момента создания записи в веб-интерфейсе.
- Полученный бонус учитывается отдельно от дохода сделок.
- Все денежные суммы в базе имеют тип NUMERIC, клиент суммирует микросуммы как целые `BigInt`; значения хранятся с 6 знаками (для бонусов 4).
- Прошедшие события учитываются в «доступно сейчас». Будущие операции не считаются уже состоявшимися.
- Если новая операция, исправление или изменение начального баланса делает временную историю баланса отрицательной, серверные функции откатывают транзакцию. Функции блокируют параллельные финансовые записи **этого пользователя** и используют UUID ключи повторных запросов для открытия сделок и операций.

## Проверки и ограничения

- В изолированном тестовом браузере Chromium с **эмулированным Supabase** проверены 6 разделов, дневные сигналы (8 за один день), даты с секундами, RPC-параметры нового пополнения и сделки, вывод денежных величин с шестью знаками, мобильная вёрстка 390 px, переключение навигации. Все тестовые суммы и сигналы вымышлены и не включены в архив.
- `node --check` для обновлённого JS пройден; ZIP/CRC проверяются при сборке.
- **Не проверены в живом Supabase**: исполнение SQL и его транзакционная целостность, политики безопасности реальной БД, конкурирующие запросы с нескольких устройств, PWA-кеш на реальном GitHub Pages, регрессия основного дневника с 2855 реальными сделками.
- Фоновая доставка сигналов по-прежнему **не реализована**: браузерные напоминания работают только с открытой вкладкой.
- Расписание не создаёт сделки автоматически; новый дневник — инструмент регистрации и анализа сигналов, а не бот исполнения.
- Внешние изменения таблиц через другие клиенты / ручные SQL могут обойти предложенный RPC-процесс и требуют отдельной проверки прав доступа. Для полного серверного запрета прямых финансовых изменений понадобится отдельный этап и аудит всех клиентов.
- История редактирования бонусов и полнофункциональный редактор расписания не реализованы; задачей этого релиза были заявленные изменения точности, дизайна и баланса.

Основной дневник и его данные не изменены. Публикация на GitHub не выполнялась.
