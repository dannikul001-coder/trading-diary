# Trading Diary 02 — V4, рабочее пространство автоматических сигналов

**Дата сборки:** 30 октября 2026 г.  **Статус:** тестовая сборка для проверки; НЕ релиз в рабочий Supabase.

## Что изменено

- **Редактирование сделок:** ставка, точное время открытия, длительность, заметка; закрытые сделки — также полный возврат и время закрытия. У каждой записи прежний UUID. Серверная операция пересчитывает всю историю баланса и сохраняет снимки `old_data` / `new_data` в таблице исправлений. Финансовые сделки нельзя удалять без согласованного процесса — вместо этого их нужно исправлять.
- **Мешочки:** создание и редактирование названия, суммы (4 знака), статуса, времени; безопасный пересчёт и журнал исправлений. «Ожидается» и «Отменён» не влияют на доступный баланс.
- **Расписание:** основной режим — события по конкретному дню, с неделей вокруг даты. Отдельные параметры сигнала: тип, инструмент, направление, описание, секунды, напоминание, включено/выключено. Редактирование, удаление с подтверждением, копирование набора сигналов с одного дня на другой.
- **Календарь:** отдельный экран с доходом закрытых сделок, числом сделок, сигналов и бонусов на каждую дату.
- **Аналитика:** фактический доход по дням, времени суток, дням недели, средний доход, число закрытых сделок и отдельные бонусы. Графики не рассчитывают «убытки» и «win rate», поскольку продукт работает только с прибыльными закрытыми сделками.
- **Планы, цели, заметки:** отдельные таблицы и CRUD. Сводка целей ручная; нельзя выдавать её за автоматически достигнутый результат.
- **Обзор:** показаны накопленные показатели и подписанные отдельно показатели сегодня, за последние 7 × 24 часов, за календарный месяц; пересчитана предложенная ставка / предложенный возврат без плавающих денежных операций.
- **Админ:** отдельный защищённый серверный отчёт по пользователям: существует ли дневник 02, сделки, доступный баланс, доход, задачи, цели, пройденные опубликованные уроки / число опубликованных уроков. Прогресс других участников недоступен обычным пользователям. В основной админке теперь тоже показывается число завершённых уроков, которое сервер уже возвращал.
- **Почта:** галочка согласия; очередь с повторными попытками, защита от повторной отправки, серверная Edge Function + Resend. Статус «Принято почтовым сервисом» не означает доставлено в почтовый ящик. Никаких API ключей во frontend.
- **Настройки:** при наличии реальных операций нельзя незаметно сменить валюту без конвертации истории. Изменения начального баланса и других параметров записываются в аудит. Добавлен JSON-экспорт собственных данных.

## Важное: какие файлы изменены

- `index.html` — меню новых разделов и колонка Learning progress в существующей админке.
- `automated-diary.css` — стили новых экранов, адаптация бокового меню.
- `js/automated-diary.js` — разделы, редактирование, финансовые проверки на клиенте, сообщения.
- `js/admin.js` — только отображение уже возвращаемого сервером `lessons_completed`.
- `sw.js` — новый ключ PWA-кэша для обновления статических файлов.
- `supabase/automated_diary_v4_workspace.sql` — новая **аддитивная миграция**: таблицы второго дневника, исправления, защита финансовых операций, почтовая очередь, административные агрегаты.
- `supabase/functions/automated-email-reminders/index.ts` — серверная отправка письма.

Остальные файлы основного дневника и исторические SQL-миграции оставлены без изменений. Никаких тестовых сделок в релизный архив не добавлено.

## Установка без риска для настоящих данных

1. Сначала сохраните полную **резервную копию реальной БД** Supabase, исходный ZIP и текущую опубликованную версию. Сверьте число сделок основного дневника и контрольные результаты.
2. Поднимите *отдельный тестовый проект Supabase* с копией схемы/нечувствительных тестовых данных. Убедитесь, что миграции `automated_diary_v1.sql` и `automated_diary_v2_timeline.sql` уже были применены. **Не применяйте их повторно без необходимости.**
3. Запустите `supabase/automated_diary_v4_workspace.sql` на тестовом проекте, внимательно проверьте все RPC и RLS. SQL не изменяет таблицу `trades` основного дневника.
4. Деплойте код и V4-миграцию как **согласованное обновление**: V4 отзывает у authenticated прямые права изменять денежные таблицы, и старый JS V3 после этого больше не сможет записывать бонусы. Это запланированное ограничение безопасности. Нельзя сначала поменять рабочую базу, оставив публичный V3.
5. Проверьте тестовым пользователем создание и исправление открытых/закрытых сделок, 8 сигналов за день, редактирование бонусов, цели и планы, конкурирующие запросы с двух устройств. Убедитесь, что отрицательный исторический баланс отклоняется, а запись не создаётся повторно. Проверьте, что второй пользователь не получает чужие записи, а обычный пользователь не может вызвать админскую RPC.
6. **Только после такого тестирования и подтверждения владельца** можно обсуждать публикацию новой версии сайта и применение миграции в рабочей базе.

## Отдельное подключение почтовых уведомлений

Это требует инфраструктуры и **не начнёт отправлять письма само по себе после загрузки ZIP**.

1. Настройте сервис Resend, верифицируйте домен отправителя. Задайте в **секретах Edge Functions** переменные `RESEND_API_KEY`, `AD_REMINDER_FROM_EMAIL`, `AD_REMINDER_JOB_SECRET`. Среда Supabase также должна предоставить `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`. Все секреты — только на сервере, никогда в JavaScript сайта.
2. Разверните серверный обработчик из `supabase/functions/automated-email-reminders/index.ts`. Он принимает только POST-запрос с секретным заголовком `x-job-secret`, принимает задания исключительно через service-role RPC и работает без публичного доступа к базе. Если выключена JWT-проверка на шлюзе Edge Functions, проверка секретного заголовка остаётся **обязательной**.
3. В Supabase Cron настройте задание раз в минуту, которое вызывает функцию через `pg_net`. Храните `AD_REMINDER_JOB_SECRET` в Supabase Vault; не вставляйте значение прямо в сохраняемый SQL или GitHub. Пример вызова с переменными: 

```sql
-- ПРИМЕР, не выполнять без подстановки URL проекта и настройки Vault!
-- Vault должен содержать secret с name = 'ad_reminder_job_secret'.
select cron.schedule('ad-reminder-every-minute', '* * * *', $$
 select net.http_post(
   url:='https://YOUR_PROJECT_REF.supabase.co/functions/v1/automated-email-reminders',
   headers:=jsonb_build_object(
     'Content-Type','application/json',
     'x-job-secret',(select decrypted_secret from vault.decrypted_secrets where name='ad_reminder_job_secret')
   ),
   body:='{}'::jsonb
 );
$$);
```

4. В настройках второго дневника пользователь добровольно включает почтовые напоминания. Доставка выполняется только на подтверждённый email из Supabase Auth. Проверьте действительную доставку тестового письма с другого аккаунта и сохранение идентификатора провайдера в очереди.
5. **Точная секунда события хранится**, но Cron с интервалом в минуту и внешний почтовый провайдер не гарантируют доставку на определённой секунде. Сбои сети, провайдера, спам-фильтры и закрытые почтовые ящики могут повлиять на фактическое получение.

## Проверки этой сборки

**Выполнено:** `node --check` для JS; изолированные unit-тесты BigInt, хронологии нескольких одновременных сделок, временных меток, календаря и формирования экранов; проверка состава ZIP, неизменности основного приложения, отсутствие вложенных тестовых данных.

**Не выполнено:** реальный Supabase и RLS, выполнение V4 SQL на PostgreSQL, отправка Resend, Cron, настоящий мобильный браузер / Chromium. Запуск браузера в среде сборки заблокирован. Нельзя называть эту сборку полноценно протестированным production-релизом.

## Известные ограничения

- Планы, заметки и цели имеют базовый CRUD, но не повторяющиеся задачи, вложения и детальную систему напоминаний.
- Админ-отчёт показывает агрегаты без доступа к персональным сделкам другого пользователя и без инструментов административного редактирования чужих финансовых записей.
- Повторяемые сигналы создаются копированием дня, а не через фоновое правило recurrence.
- Нет подтверждения фактического результата email-доставки в почтовый ящик: `accepted` — только ответ API провайдера.
- Полноценное end-to-end тестирование необходимо до выпуска. Если ещё не выполнена миграция V4, UI выдаст понятную ошибку загрузки, а не будет имитировать сохранение.
